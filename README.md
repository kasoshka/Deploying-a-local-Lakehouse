## 2. Поднятые сервисы — и почему именно они

Перечисли, что реально поднял (проверь через `docker ps`), и обоснуй выбор каждой технологии.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| silo  | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Поддерживает S3 API, уже включён в пример Lakekeeper, не нужно настраивать отдельно |
| Postgre | База для метаданных Lakekeeper | Надёжная СУБД, официально поддерживается Lakekeeper |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Легко подключается к Trino, не нужен Hive Metastore |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Открытый исходный код, быстрый, умеет читать Iceberg и генерировать TPC-H данные |
| starrocks | Альтернативный SQL-движок из демо-стека Lakekeeper. В Q16 не использовался. | StarRocks быстрый на OLAP-агрегациях и умеет читать Iceberg, но для одного запроса Q16 на sf1 это не даёт выигрыша. Trino уже решает задачу и нативно работает с Lakekeeper, поэтому StarRocks оставили как есть, но не использовали. |
| jupyter | Присутствует в минимальном примере Lakekeeper как альтернативный движок. Для Q16 не использовался. | Jupyter удобен для исследования данных и Python-кода, но Q16 — чисто SQL-задача, и Trino закрывает её без Python. Поэтому Jupyter оставили без изменений, в медальоне он не участвует. |

### Скрипты, которыми поднимал стек

Вставь свои команды (`docker run` / `docker-compose.yml` / shell-скрипт), которыми реально поднял сервисы, с кратким комментарием к каждой.

```bash
# 1. Клонирование официального репозитория Lakekeeper
git clone https://github.com/lakekeeper/lakekeeper.git

# 2. Переход в минимальный демо-пример (в нём уже есть Lakekeeper, PostgreSQL,
cd lakekeeper/examples/minimal

# 3. Запуск всего стека в фоне
docker compose up -d

# 4. Проверка, что контейнеры поднялись и здоровы
docker ps

# 5. Просмотр потребления памяти каждым контейнером (для обоснования масштаба)
docker stats --no-stream
```

## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| part | partkey, brand, type, size | Фильтрация деталей и группировка по бренду, типу и размеру. Джойнится с partsupp.|
| partsupp | partkey, suppkey | Соединение деталей с поставщиками и подсчёт количества разных поставщиков. Джойнится с part по partkey. |
| supplier | suppkey, comment | Используется в подзапросе (анти-джойн): исключает поставщиков, у которых comment LIKE '%Customer%Complaints%' |


## 4. Медальон — решения по каждому слою

Как заполнять:
- **Строк** — `SELECT count(*) FROM таблица`;
- **Вес, МБ** — размер файлов таблицы в MinIO (консоль → бакет → объекты) или `SHOW STATS`;
- **Формат** — `PARQUET` / `ORC`;
- **Сжатие** — `NONE` / `SNAPPY` / `GZIP` / `ZSTD`;
- **Партиционирование** — по какой колонке (или «нет»);
- **Обоснование** — почему выбрал именно такой формат + сжатие + партиционирование для этого слоя и твоего объёма данных.

### Bronze (сырой)

|---|---|---|---|---|---|---|---|
| `bronze.part` | все | 200 000 | 4.2 | PARQUET | ZSTD | нет | Bronze хранит сырые данные без изменений. Parquet — стандарт для Lakehouse, SNAPPY — дефолтное сжатие Trino. Партиционирование не делаем из-за малого объема. |
| `bronze.partsupp` | все | 800 000 | 28.0 | PARQUET | ZSTD | нет | Самая тяжелая таблица в слое. |
